# Prisma Strategy

This document outlines our approach to utilizing Prisma ORM in the Cotizador 2.0 Enterprise project.

## Location & Setup

Prisma configuration is centralized in the `packages/database` module of our monorepo.

```text
packages/database/
├── prisma/
│   ├── schema.prisma      # The single source of truth for the DB schema
│   ├── migrations/        # SQL migration files generated by Prisma
│   └── seed.ts            # Enterprise data seeding script
├── src/
│   ├── index.ts           # Exports the generated Prisma client
│   └── prisma.service.ts  # NestJS injectable Prisma Service (if exposed here)
├── package.json
└── tsconfig.json
```

## Prisma Client Generation

The Prisma Client must be generated into the `node_modules` of the `packages/database` directory or exported explicitly. Apps (like `apps/api`) will consume it via `@cotizador/database`.

## Migrations Strategy

1. **Development**: Use `npx prisma migrate dev` to generate migrations locally based on schema changes. Name migrations descriptively (e.g., `add_user_roles`).
2. **Production**: Use `npx prisma migrate deploy` in the CI/CD pipeline. NEVER run `migrate dev` or `db push` in production.
3. **Squashing**: Periodically squash migrations if the migration history becomes too slow or unwieldy for CI.

## Performance & Connections

- **Connection Pooling**: In serverless/highly scaled environments, use Prisma Accelerate or PgBouncer to manage connection limits.
- **Client Instantiation**: Ensure the NestJS `PrismaService` is a singleton and properly hooks into `OnModuleInit` and `OnModuleDestroy` to manage connections lifecycle gracefully.

## Seeding

Maintain robust seeders in `prisma/seed.ts` for:
- **Base Data**: Roles, Permissions, Config states needed for production.
- **Mock Data**: Fake data used strictly in development/staging environments (guarded by `NODE_ENV`).
