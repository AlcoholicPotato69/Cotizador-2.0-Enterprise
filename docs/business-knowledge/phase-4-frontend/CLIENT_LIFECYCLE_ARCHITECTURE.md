# CLIENT LIFECYCLE ARCHITECTURE (Fase 4.3.1)\n\nLa información del cliente (Expediente Único) representa la base de toda la integridad referencial de la plataforma. Por ello, el ciclo de vida del cliente obedece reglas estrictas de inmutabilidad.\n\n## 1. Estados del Ciclo de Vida\nTodo cliente en Cotizador 2.0 Enterprise transita por una máquina de estados:\n\n- **\`active\`**: El cliente opera normalmente. Puede generar cotizaciones, firmar contratos y emitir facturas. Su expediente documental está validado.\n- **\`inactive\`**: El cliente está bloqueado temporalmente (ej. por adeudos o auditoría pendiente). No se le pueden emitir nuevas cotizaciones ni contratos, pero el histórico permanece consultable.\n- **\`archived\`**: El cliente cesó operaciones definitivas con el Tenant. **Prohibido el borrado físico (Hard Delete)** si el cliente tiene al menos una cotización, contrato o factura en su historial para garantizar la integridad de la base de datos financiera.\n\n## 2. Prevención de Borrado\nSi se intenta ejecutar \`client.delete\`, el Backend validará las relaciones Foráneas (Foreign Keys). Si existe historial, el sistema forzará un \`Soft Delete\` cambiando el status a \`archived\` e inyectando un registro en el *Audit Trail*.\n\n## 3. Matriz de Contactos (Preparación Futura)\nLa entidad Cliente evolucionará de un contacto singular a una corporación con múltiples *Stakeholders*.\nLa arquitectura de base de datos se preparará para recibir un array relacional \`client_contacts\` categorizado por:\n- **Contactos Principales**: Dueño o Representante Legal (único firmante de contratos).\n- **Contactos Secundarios**: Operadores o gerentes de área.\n- **Contactos Financieros**: Áreas de Cuentas por Pagar (receptor de CFDI y notificaciones de cobranza).\n- **Contactos Legales**: Abogados o despachos encargados de validar las cláusulas contractuales.
