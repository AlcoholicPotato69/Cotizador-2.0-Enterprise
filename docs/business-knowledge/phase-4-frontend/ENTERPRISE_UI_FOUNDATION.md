# ENTERPRISE UI FOUNDATION (Fase 4.2.1)\n\nEste documento decreta la centralización absoluta del Design System. Se prohíbe terminantemente que cualquier módulo de negocio (Cotizaciones, Contratos, Finanzas) invente componentes visuales, tipografías, colores o layouts.\n\n## 1. Page Foundation\nTodas las pantallas principales deben usar el **\`DsPageHeader\`**. Éste centraliza:\n- Breadcrumbs.\n- Título y Subtítulo.\n- \`DsStatusBadge\` (cuando aplique).\n- \`DsActionBar\` (cuando haya acciones).\n\n## 2. Action Foundation\nCualquier barra de herramientas o botonera que ejecute cambios de estado debe utilizar **\`DsActionBar\`**. Este componente filtra automáticamente los botones internos mediante \`usePermissions().can()\`. Si un usuario no tiene \`contract.approve\`, el botón jamás será renderizado en el DOM.\n\n## 3. Form Foundation\nTodos los inputs (DsInput, DsSelect, etc.) deben envolverse obligatoriamente en un **\`DsFormField\`**. Este componente centraliza la etiqueta (Label), los indicadores de requerimiento (\`*\`), el texto de ayuda (Hint) y la inyección del mensaje de error visual (border-red-500) sincronizado con el Engine de validación.\n\n## 4. Status Foundation\nExiste un catálogo inmutable y único de estados visuales:\n- \`draft\` / \`pending\` / \`approved\` / \`rejected\` / \`cancelled\` / \`active\` / \`completed\` / \`paid\` / \`unpaid\` / \`overdue\` / \`reserved\` / \`blocked\`.\n\nEl componente \`DsStatusBadge\` es el dueño de la semántica de color. Ningún módulo dibujará sus propias insignias de estado.\n\n## 5. Calendar Foundation\nEl **\`DsCalendarShell\`** es un lienzo agnóstico. Es incapaz de calcular lógica de negocio. Solo pinta matrices visuales que le ordena el backend, soportando las reglas topológicas de \`Casa de Piedra\` (reservas topológicas/salones) y \`Plaza Mayor\` (activaciones/publicidad digital temporizada).
