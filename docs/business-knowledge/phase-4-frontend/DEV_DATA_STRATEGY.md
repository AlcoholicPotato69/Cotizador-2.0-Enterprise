# DEV DATA STRATEGY (Fase 4.3.2)\n\nPara evitar que los desarrolladores inviertan tiempo creando registros manualmente durante la validación visual, se implementa una estrategia de **Seed Engine**.\n\n## 1. Naturaleza de los Datos Demo\nLos datos deben representar los Casos de Uso más agresivos y completos (Edge Cases):\n\n### Clientes Demo\n- **Empresa PM Activa**: \`Coca-Cola FEMSA S.A.B. de C.V.\`, con 4 documentos aprobados, referenciada en Plaza Mayor.\n- **Persona Física Bloqueada**: \`Juan Pérez\`, estatus \`inactive\`, con documentos marcados como faltantes.\n- **Empresa CP Nueva**: \`Expo Poliforum\`, estatus \`pending\`, referenciada en Casa de Piedra.\n\n### Contratos y Cotizaciones Demo (Fases 4.4 - 4.6)\n- Contrato con esquema financiero a 12 meses (pagos parciales).\n- Cotización caducada con descuentos escalonados.\n\n## 2. Seed Engine (npm scripts)\nSe crearán los siguientes scripts de automatización en \`package.json\` e inyectables desde el \`DevToolbar\`:\n\n- **\`npm run seed:dev\`**: (En PocketBase local) Borra todas las colecciones principales (precaución: solo tablas derivadas, no *sys_config*) e inserta los *JSON Fixtures* de Clientes, Contratos y Cotizaciones Demo.\n- **\`npm run reset:dev\`**: Devuelve la base de datos a un estado "Empty State", ideal para probar las validaciones gráficas como \`DsEmptyState\` y \`DsLoadingState\`.\n\n## 3. Usuarios Simulados (Mock Auth)\nEl array de usuarios simulables (disponible solo en DEV) contendrá:\n1. \`SuperAdmin\` (Bypass Total)\n2. \`Comercial PM\` (Limita a crear cotizaciones y clientes en PM)\n3. \`Finanzas PM\` (Limita a ver contratos, aplicar pagos y conciliación bancaria PM)\n4. \`Operaciones PM\` (Limita a ver disponibilidad de calendario y mantenimientos PM)\n5. \`Comercial CP\` \n6. \`Finanzas CP\` \n7. \`Operaciones CP\`
