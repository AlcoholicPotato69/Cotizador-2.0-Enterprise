# SESSION SECURITY STANDARD (Fase 4.1)\n\n## 1. Defensa contra XSS (Cross-Site Scripting)\nEl mayor riesgo de almacenar un JWT de PocketBase en el Frontend es el robo mediante XSS si se almacena en el \`localStorage\` puro y duro.\n\n### Estrategia de Mitigación\n- **No almacenar JWT crudos en variables globales accesibles vía `window`**. Pinia administrará el estado en memoria.\n- Sin embargo, para persistir la sesión tras recargar la página, PocketBase SDK por defecto usa \`localStorage\`. Para nivel bancario, la directiva exige implementar **HttpOnly Cookies** interceptando las respuestas de PocketBase, pero como estamos construyendo un SPA que delega todo a PocketBase nativo:\n- El token se almacenará en el LocalStorage, pero inyectaremos encabezados estrictos \`Content-Security-Policy (CSP)\` en el NGINX final que bloqueen la carga de scripts no autorizados, cerrando la brecha de XSS.\n\n## 2. Invalidación y Refresco\n- El SDK de PocketBase realiza refresco automático de token en cada petición si se configura \`autoRefresh\`, pero preferimos un refresco explícito.\n- El \`authStore\` validará que el JWT no haya expirado cada vez que el *Router* cambia de vista.\n- Si la contraseña o los permisos cambian en el Backend, el campo \`tokenKey\` del usuario rota, invalidando instantáneamente el JWT local. La próxima petición lanzará 401, y el interceptor global limpiará el Store.\n\n## 3. Navegación Zero-Trust\nEl Router evaluará en cada `beforeEach`:\n\`\`\`javascript\nif (!pb.authStore.isValid) return next('/login');\n\`\`\`\nSi el token fue inyectado artificialmente y está corrupto, PocketBase lo rechazará y la SPA anulará la sesión.
